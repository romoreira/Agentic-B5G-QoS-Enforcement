# BESS UPF DPDK Baseline Campaign Notes

This document records the preliminary baseline campaign executed before the agentic controller experiments. It is meant to help resume the work later without reconstructing the operational context from memory.

## 1. Purpose

The goal of this campaign is to validate the non agentic baselines over the five slice BESS UPF DPDK testbed before introducing the LLM based controller.

The campaign establishes that the following components are working together.

1. BESS UPF in DPDK mode with Mellanox mlx5 PMD
2. PFCP control through the dedicated control interface
3. Five active PFCP sessions representing five slices
4. Per slice QoS enforcement through app level QER MBR values
5. TRex traffic generation over N3 and packet reception over N6
6. Remote collection of UPF and BESS counters over SSH
7. Repeatable baseline execution with 10 runs per controller

The agentic controller is not part of this campaign. This campaign is the baseline foundation for later comparison.

## 6. Traffic phases

Each run has four phases.

```text
Phase A
Steady state
Duration 60 s
All slices offered below their cap

Phase B
Bronze burst
Duration 60 s
S5 is overloaded

Phase C
Silver flash crowd
Duration 60 s
S3 and S4 are overloaded together

Phase D
Recovery
Duration 60 s
All slices return to normal load
```

The effective elapsed time between snapshots is around 84 to 92 s because it includes traffic duration, waiting margin, TRex console interaction, and remote snapshot collection.

## 7. Experiments in this baseline campaign

The campaign executes three non agentic baselines.

```text
E1 Static
No runtime MBR adaptation
The initial MBR vector is kept during all phases

E2 Threshold
A simple conservative baseline
It applies predefined MBR changes before overloaded phases

E3 Greedy
A simple utilization oriented baseline
It reallocates MBR toward the currently stressed slice group
```

These baselines are not the final contribution. They provide comparison points for the later agentic controller.

## 8. Script behavior

The campaign script performs the following procedure for each experiment and each run.

```text
1. Reset app MBRs to the initial vector
2. Collect a before snapshot from the UPF
3. Run phase A through TRex
4. Wait until the phase finishes
5. Collect phase A snapshot from the UPF
6. Apply controller action if required
7. Run phase B
8. Collect phase B snapshot
9. Apply controller action if required
10. Run phase C
11. Collect phase C snapshot
12. Restore the initial vector if required
13. Run phase D
14. Collect phase D snapshot
15. Collect final after snapshot
16. Store TRex console output and controller action log
```

The script must be executed from the TRex host.

```bash
RUNS=10 ~/agentic_qos_scripts/run_baseline_campaign.sh
```

The TRex server must be running in another terminal or through nohup.

```bash
cd /opt/trex/v3.08
sudo ./t-rex-64 -i --no-ofed-check -c 8
```

## 9. Important troubleshooting lessons

### 9.1 TRex server must be running

If `t-rex-64` is not running, `trex-console` fails with the following message.

```text
Failed to get server response from tcp://localhost:4501
```

In that case, the campaign may still wait for the phase duration, but no traffic is generated. The analysis then reports zero or near zero packet deltas.

### 9.2 trex-console start is asynchronous

The `start -d 60` command does not block the shell for 60 s. The campaign script was patched to explicitly sleep for the phase duration before collecting stats and snapshots.

The corrected behavior is the following.

```text
start traffic
sleep for PHASE_DURATION
collect TRex stats
collect UPF snapshot
```

### 9.3 pfcpsim and UPF session state must match

The UPF can show five PFCP sessions while a newly restarted `pfcpsim` no longer knows those sessions internally. In this case, `session modify` fails with the message below.

```text
Not enough active sessions
```

The clean fix is to restart the UPF pipeline and `pfcpsim`, then recreate the five sessions once.

### 9.4 Do not run session create twice

Running `session create` twice creates duplicate sessions on the UPF side. If this happens, delete the sessions or reset the UPF pipeline before continuing.

The target state before a campaign is shown below.

```text
pfcp_sessions 5
pdrLookup 10 rules
farLookup 10 rules
appQERLookup 20 rules
sessionQERLookup 10 rules
```

The script checks the following items.

```text
Positive packet deltas
PFCP sessions equal to 5
PDR lookup failures equal to 0
FAR lookup failures equal to 0
Bad route packets equal to 0
NIC drops absent or very small
TRex console output without real execution errors
Snapshot elapsed time compatible with a complete phase
```

## 11. Baseline campaign result

The official 10 run baseline campaign produced the following sanity result.

```text
Run directories found       30
Total phase records         120
OK phase records            100
WARN phase records          20
FAIL phase records          0
```

The warning records were caused by tiny N3 NIC receive drops. These were very small and did not coincide with PDR failure, FAR failure, bad route packets, or N6 transmit drops. Therefore, they were interpreted as acceptable warnings for the preliminary baseline campaign.

The health status by experiment was as follows.

```text
e1_static
OK      32
WARN     8

e2_threshold
OK      34
WARN     6

e3_greedy
OK      34
WARN     6
```

The preliminary aggregate means computed from `phase_summary.csv` were as follows.

```text

Access RX packets mean        29,999,810
Core TX packets mean          24,800,066
App QER meter red mean         5,199,745

e2_threshold
Access RX packets mean        29,999,850
```

This confirms that E1 and E3 delivered similar aggregate throughput, while E2 was more conservative and delivered less Core TX traffic on average.

The detailed sanity output showed 30 run directories, 120 analyzed phase records, 100 OK records, 20 WARN records, and 0 FAIL records in the campaign. The warnings were tiny NIC drops with zero PDR failures, zero FAR failures, and zero bad route packets. This supports using the campaign as a valid baseline data source for the next analysis stage.

## 12. Current interpretation

The preliminary results suggest the following.

```text
E1 Static provides the default no adaptation baseline.
E2 Threshold is more conservative and lowers delivered Core TX during overload.
E3 Greedy behaves close to E1 in aggregate delivered traffic.
The useful differences are likely phase dependent rather than only visible in global averages.
Phase B and phase C should be analyzed separately.
```

```text

12. Run analyse_results.py
13. Inspect sanity_report.md
```
